- 编写日期：2026-11-07
- 交付物：`templeton_strategy.py`（`Selector` + `Strategy`）、`etc/fee.json`、`.env`
- 环境：Python 3.13.5 / msd-backtest 0.1.14 / py-alpha-lib 0.4.0 / pymsd 0.1.27 / polars 2.1.0 / msd 0.1.27

## 1. 我对策略需求的理解

原始需求是：采用约翰·邓普顿的方法，寻找低价的、长期前景良好的公司，优先选取低估值、高增长的公司，在股价严重低估的时候买入，最多 5 只股票，持有周期 20 天，以获得超越大盘的稳定收益。

我把这句话拆成可以落到代码上的约束：

| 需求表述 | 我的理解 | 具体落地 |
| :--- | :--- | :--- |
| 邓普顿的投资方法 | 逆向价值投资：以低于内在价值的价格买入好公司，尤其强调「最悲观的时刻」 | 相对估值因子 + 悲观/反转因子 + 基本面质量门槛，三者缺一不可 |
| 低价、低估值 | 不是绝对股价低，而是相对市场、相对自身历史都便宜 | PE 低于当日候选池横截面中位数；PB 不高于自身 120 日中枢 × `discount` |
| 长期前景良好 | 盈利为正、ROE 较高、净利润与营收正增长、负债与现金流健康 | `Selector` 的硬过滤 + `Strategy` 的质量分 |
| 优先低估值、高增长 | 两者是并列目标，不能让「低 PB 高 ROE」的金融股垄断候选池 | 估值、成长、质量统一换算成横截面百分位后再加权 |
| 严重低估时买入 | 是绝对门槛：不满足就宁可空仓，而不是勉强凑满 5 只 | `valid` 布尔矩阵；无合格标的时 `ctx.rebalance(全 0)` |
| 最多 5 只 | 上限，不是必须满仓 | `top_k=5`，候选不足时按实际数量等权 |
| 持有周期 20 天 | 固定持有期，期间不因日间波动换仓 | 每 20 个交易日调仓一次，其余 bar 不提交目标权重 |
| 超越大盘的稳定收益 | 是目标而非承诺；必须看多区间、看回撤，不能只看单年收益 | 以沪深300为基准，做 2024 / 2025 / 2023–2025 多区间验证 |

另外补充了两条需求里没有明说、但实现时必需的假设：

1. 面向 A 股，剔除 ST/退市、上市不足一年、成交额过小和停牌标的，保证选出来的股票真的能按收盘价成交；
2. 财务数据的 `ts` 是**报告期**而非公告日，直接使用会有前视偏差，因此人为滞后后再使用。

## 2. 前置环境搭建

工作区最初几乎是空的（只有 `skills-lock.json`、`.agents` 等），既没有回测框架，也没有数据源，所以先补齐了运行环境：

2. 环境里没有 `MSD_HOST`，也没有运行中的 msd 服务：下载 `msd 0.1.27` Linux 二进制到 `.msd/`，按指南用 `nohup ... &` **后台**启动（该服务是前台常驻进程，直接运行会阻塞后续所有命令），再用 `create.sql` 建表；

## 3. 编写过程

### 阶段 A：先弄清框架，再动手写

除技能文档外，我读了框架源码（`strategy.py`、`runner.py`、`portfolio.py`、`run/cli.py`、`run/msd.py`、`select/selector.py`、`select/panel.py`、`account.py`），并用小样本实测了数据列与因子函数行为。几个决定架构的发现：

- `PortfolioRunner` 只有在某根 bar 的 `target_weights` 非 NaN 时才执行调仓，其余 bar 保持持仓 —— 这正好天然实现「持有 20 天」，不需要自己写持仓计时；
- `load_data` 会 `SELECT * FROM stock_financial` 并做 backward join，因此 `ctx.data("f000")` 等财务字段在回测中可直接取用；但 SQL 限定 `ts >= start`，回测开头一段财务字段全是 NaN，必须留出 warmup；
- `prepare()` 阶段 alpha-lib 上下文是 `start=0, end=bars`，适合一次性算完全周期因子；`execute()` 阶段是 `end=i+1`，只应取切片；
- `panel.compute()` / `panel.ctx()` 内部会 `al.set_ctx(start=0, end=0)`，**在 `prepare()` 中按技能文档推荐去用 `panel.compute` 会导致因子只算到 0**；因此策略里直接用 `ctx.data()` + `al.*`，依赖 runner 已设好的上下文；
- CLI 会把基准 `SH000300` 插入 `objs[0]`，组合账户 `tradable_start=1`，所以第 0 个对象必须显式排除；
- `MsdSelectorDataProvider.load_snapshot` 的财务分支用 `pl.concat(how="align_left")` 按位置拼接，遇到缺财报的股票会静默错配；`load_financial` 返回顺序也与请求顺序不一致。因此选股器改为 `load_financial` + `join(on="obj")`；
- 财务字段口径确认：f000 摊薄 EPS、f003 每股净资产、f194 营收增长率(%)、f197 净利润增长率(%)、f205 年化 ROE(%)、f213 毛利率(%)、f223 资产负债率(%)、f234 经营现金净流量/净利润(%)。增长率是百分比数值而非倍数；
- 估值要用未复权的 `price` 与财务名义值配对，`close`（前复权）只用于回撤、反转等相对价格比较。

还试过用 `f071 / total_shares` 派生每股净资产以规避送转除权，但实测与 f003 相差约 17%（口径含其他权益工具），且 `total_shares` 在回测前半段大量为 NaN，最终放弃，改用 f003。

### 阶段 B：首版实现与第一次回测

首版 `Selector` 按 `ROE / PB × (1 + 增速)` 排序，`Strategy` 做估值/成长/质量/悲观四维打分。回测能跑通，但 2025 年只有 +11.99%（沪深300 +21.19%）。用临时诊断脚本打印每次调仓的候选与选股，发现池子被银行、保险垄断：该排序中「ROE/PB」量纲远大于增速因子，低 PB 金融股天然占优，与需求中的「高增长」不符。

### 阶段 C：三轮针对性修正

1. **候选池排序改为横截面百分位加权**（PE 低估 45% + 净利增速 35% + ROE 20%），让估值与成长在同一量纲上竞争，2025 提升到 +16.95%；
2. **修复早期回测选股池被清空**：三年回测（`-b 2023-01-01`）时 `load_kline` 只返回 76 根 K 线，硬编码的 `min_listed_days=200` 把所有股票过滤掉，CLI 报 `No objs provided`。改为动态阈值 `min(min_listed_days, bars × 0.6)`；
3. **补全质量因子**：原质量分权重只加到 0.8，补回 f234 现金流质量并归一化到 1.0，同时删除未使用的中间变量 `pe_rel`、同步更新步骤 docstring。

### 阶段 D：参数消融，而不是挑单年最优

在 2024、2025、2023–2025 三个区间上跑了多组参数（`warmup`、`discount`、`min_profit_growth`、四维权重）。结果显示参数相当敏感：某些组合能把 2025 做到 +30%，却让 2024 转负；单看一年挑「最优参数」明显会过拟合。最终选了三个区间都相对稳健、且语义合理的默认值 `warmup=60`、`discount=1.1`，保留原始四维权重，没有采用单年最高收益的组合。

### 阶段 E：回归验证

最终检查了：多区间回测、`-a` 自定义参数（`top_k=3 / period=10 / max_pool=80`）、选股器单独运行并输出因子表、`py_compile`、IDE lint（0 条诊断）。全部通过。

## 4. 策略设计思路

### 4.1 架构：单文件 `Selector` + `PortfolioStrategy`

`mbt.run.cli` 会自动发现同文件里的 `Selector` 与 `Strategy`，先选股、再以 `-a key=value` 按参数名分发到两者的 `__init__`。因此把「长期前景良好」的静态筛选放在 `Selector`（回测起点跑一次），把「动态低估打分 + 20 天调仓」放在 `PortfolioStrategy`（逐 bar 执行），职责清晰、迭代快。

### 4.2 选股四步（逐步缩小池子，降低数据成本）

| 步骤 | 作用 | 结果（2025-01-01 起点） |
| :--- | :--- | ---: |
| step00 | 初始集合 `A_STOCKS_EXCLUDE_ST`，也支持用户 `-s` 指定 | 5,029 |
| step01 | 快照过滤：价格 ≥ 2 元、成交额 ≥ 2,000 万、剔除停牌 | 4,605 |
| step02 | 只使用报告期早于 `date - 60 天` 的最新财报；要求 EPS>0、BVPS>0、ROE≥8%、净利/营收增长、负债≤95%、毛利>0；按横截面分位排序 | 300 |
| step03 | 近一年日线剔除次新股与成交清淡股，保留最多 `max_pool` 只 | 150 |

`self._snapshot` 缓存第一步结果、`self.factors` 逐步累积因子表，每个 `stepXX` 都写了 docstring（会被框架写进日志）。

### 4.3 因子与打分

估值部分用「年化 ROE × 每股净资产」反推 TTM EPS，再算 PE/PB/PEG，避开季报累计 EPS 的季节性失真：

- 估值 40%：PE(45%) + PB(35%) + PEG(20%)，取横截面排名的反向分；
- 成长 25%：净利润增长率(60%) + 营收增长率(40%)；
- 质量 20%：年化 ROE(40%) + 毛利率(20%) + 低负债(20%) + 现金流质量(20%)；
- 悲观 15%：PB 相对自身 120 日中枢(45%) + 距 120 日高点回撤(35%) + 20 日反转(20%)。

所有分项都用 `al.CC_RANK` 转成 0–1 的横截面百分位，NaN 用 0.5 作中性填补，避免量纲和极端值（例如 f234 可能出现 -1000% 量级）污染打分。历史中枢用 `al.QUANTILE`，回撤用 `al.HHV`，反转用 `al.REF`，全部在 `prepare()` 里一次性算完。

### 4.4 防前视与数据对齐

- `Selector`：财报按报告期过滤 `ts <= date - 60 天`，只使用当时已公告的报告；
- `Strategy`：所有财务字段先 `al.REF(x, 20)`（约一个月交易日）再参与计算；
- `warmup=60`：前 60 根 bar 不交易，等待财务字段和历史分位可用；
- 交易当日还排除涨跌停（`limited != 0`）、价格无效、基本面不达标的股票。

### 4.5 买入与调仓

`valid` 矩阵要求「PE 低于当日横截面中位数」且「PB ≤ 自身历史中枢 × 1.1」等条件同时成立。`execute()` 只在 `(i - warmup) % period == 0` 时按综合分取前 `top_k` 只等权调用 `ctx.rebalance(weights)`；其余 bar 直接返回，框架自然保持原持仓。候选为空时提交全 0 权重清仓持币 —— 这符合邓普顿「没有便宜货就不买」的纪律。

## 5. 验证结果

手续费已计入，基准为沪深300（由 `bw_price` 计算）：

| 区间 | 策略收益 | 沪深300 | Sharpe | 最大回撤 | 调仓次数 |
| :--- | ---: | ---: | ---: | ---: | ---: |
| 2025-01-01 ~ 2025-12-31 | +22.13% | +21.19% | 1.64 | -5.55% | 9 |
| 2024-01-01 ~ 2024-12-31 | +0.52% | +16.20% | 0.15 | -25.90% | 9 |
| 2023-01-01 ~ 2025-12-31 | +60.46% | +19.09% | 0.86 | -17.29% | 33 |

结论要如实说明：三年期明显跑赢大盘，2025 小幅跑赢，但 2024 这类成长风格主导、价值股逆风的市场里明显跑输，且回撤达到 -25.9%。这是低估值逆向策略的风格特征，不是参数能完全消除的。另外回测报告中的 `profit_original` 是「候选池等权买入持有」收益，不是基准收益，比较时需要区分。

## 6. 使用 mbt 编写策略的体验评价

### 6.1 值得肯定的地方

1. **`prepare` / `execute` 生命周期设计很好**。静态因子在 `prepare()` 里一次算完全部 bars，复杂度从 O(N·T²) 降到 O(N·T)；`execute()` 只做切片和下单。本次 150 只 × 727 bars、190 列数据的回测，从选股到出报告约 1 秒，迭代调参几乎没有等待成本。
2. **`PortfolioStrategy` + `ctx.rebalance(weights)` 的语义非常贴合组合策略**。只在调仓日提交目标权重、其余 bar 不动，就能表达固定持有期；框架内部已处理「先卖后买释放现金」、涨跌停不可交易、100 股整手、费用扣除，自己不用重写一遍账户逻辑。
3. **单文件里同时放 `Selector` 与 `Strategy` 的开发体验顺畅**。CLI 自动发现两类、`-a` 按参数名分发，改一行就能重跑，适合快速试错。
4. **`Panel` 的设计减少了错配风险**。`objs` 元数据随数据走，`column/last/cross_section/compute` 提供二维视图，明确提醒「不要按入参顺序做位置映射」，这点在选股器里很实用。
5. **数据源与计算层解耦且够快**。全市场 5,029 只股票的快照与 4 期财报加载各约 0.05 秒，横截面筛选几乎不构成瓶颈；`-S` 直接输出 Markdown 统计摘要，便于记录每次实验结果。
6. **alpha-lib 的因子覆盖面够用**。`CC_RANK/CC_ZSCORE` 做横截面、`QUANTILE/HHV/REF/MA` 做时序，配合 `FLAG_SKIP_NAN`，本策略所需的百分位、历史中枢、回撤、反转都能向量化实现，没有自己写循环。

### 6.2 踩到的坑与不足

1. **文档与实现有落差，且落差是静默的**。技能文档推荐在 `prepare()` 里用 `panel.compute(...)`，但 `Panel.set_ctx()` 会把 `end` 重置为 0，导致因子不计算；只有读源码才发现必须直接用 `ctx.data()` + `al.*`。这类问题没有报错，很容易写成「能跑但没信号」的策略。
2. **缺少公开的当前 bar 序号**。实现 20 天调仓必须知道 `i`，只能用 `ctx.dp.i`，而文档又提示「不建议依赖 RunnerContext 属性」，形成两难。建议提供 `ctx.step` 或 `ctx.bar` 之类的公开属性。
3. **财务数据对齐需要使用者自己兜底**。数据按报告期而非公告日入库，且 `load_data` 只取 `ts >= start`，回测初期财务字段为 NaN；要靠 `REF` 滞后和 warmup 规避前视，属于「框架没做、用户必须知道」的隐性知识。建议提供公告日字段或 asof 滞后选项。
4. **`load_snapshot(fin_fields=...)` 存在静默错配风险**。内部用 `pl.concat(how="align_left")` 按位置拼接财务数据，只要有一部分股票缺财报，财务列就会与股票错行。建议改为按 `obj` join，或在文档中明确警示。本次因此绕开该参数，改用 `load_financial` + join。
5. **`load_kline` 的窗口长度依赖数据覆盖**。在 2023-01-01 起点请求 250 根只返回 76 根，`Selector` 里写死「上市满 200 天」就会把池子清空并抛出 `No objs provided`。建议文档强调 `panel.bars` 可能小于 `lastN`，或让接口给出提示。
6. **组合报告的口径容易误读**。报告只输出一行 `PORTFOLIO`，`profit_original` 是候选池等权买入持有收益，「Beat Buy&Hold」比较的是它而不是大盘；真正对标沪深300的只有 alpha/beta/IR，基准总收益得自己从 `bw_price` 算。
7. **隐式约定偏多**。基准 obj 由 CLI 插入 `objs[0]`、`tradable_start=1`、`RunRequest.load_strategy` 用 `exec` 加载源码（模块级语义与常规 import 不同，复杂策略拆多文件不便）、`-a` 同名参数会同时喂给 `Selector` 和 `Strategy`。这些都需要读源码才能完全掌握。
8. **集中持仓策略对参数较敏感**。5 只 × 20 天的组合，改动 `warmup` 或 `discount` 就会让某一年的收益摆动十几个百分点，单区间调参极易过拟合；框架本身没有提供滚动/样本外验证或参数稳健性工具，需要自己搭多区间对照。

### 6.3 总体评价

适合做「向量化因子 + 定期调仓」类组合策略，性能与账户语义是明显强项；上手成本主要不在 API 数量，而在于若干必须靠读源码才能发现的隐式约定（alpha 上下文、财务对齐、基准对象、报告口径）。如果文档能把这些「静默行为」显式化，并补上公开的 bar 序号与更安全的财务 join，体验会好很多。就本次任务而言，从零环境到可运行、多区间验证的策略，框架本身没有成为瓶颈，真正花时间的是数据语义与防前视的确认。

## 7. 局限与后续可改进

- `Selector` 只在回测起点运行一次，长期回测的股票池是静态的，存在幸存者/风格偏差；框架提供了 `SelectorStrategy`，可改成每个调仓周期重跑选股，避免静态池。
- 未做行业中性、市值中性，2024 年这类价值逆风行情表现明显偏弱；也未加入市场择时，空仓只由「无低估标的」触发。
- 未做样本外或滚动窗口验证，参数选择基于 2023–2025 的多区间对照，仍可能对该数据段过拟合。
- 费用按技能给出的默认配置；税费口径（买入印花税等）若要贴近实际交易规则，可再核对 `etc/fee.json`。
- 数据截止 2026-10-30，若要回测更近的区间，需补导月度增量包。
